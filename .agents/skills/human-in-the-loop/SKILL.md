# SKILL: human-in-the-loop

> Для кого: 🏗️ Codex (backend-логика пайплайна), 🎨 Gemini/Antigravity (UI-слой подтверждений). Читать перед реализацией любого шага пайплайна apply (`docs/ARCHITECTURE.md` §4).

## Зачем этот скилл

Это ядро всей модели безопасности продукта: пользователь не доверяет облаку и не должен обнаружить, что что-то в его Telegram изменилось без его явного, осознанного согласия. Пайплайн apply (collect → классификация → plan-манифест → правки → подтверждение → snapshot → throttled apply → audit log → undo) — единственный путь, которым мутации вообще происходят.

## Жёсткие правила пайплайна

1. **Read-only по умолчанию (FR-17).** Assisted-режим (в котором мутации вообще возможны) включается явным действием пользователя, не является состоянием по умолчанию ни при первом запуске, ни после обновления.
2. **Dry-run обязателен перед любым реальным apply (FR-18).** Предпросмотр показывает: какие чаты затронуты, какое действие к каждому применяется, что произойдёт с лимитами папок (FR-19). Dry-run не делает ни одного мутирующего вызова к Telegram.
3. **Plan-манифест редактируется пользователем до подтверждения (FR-09/FR-10).** UI обязан позволять точечную правку (drag-and-drop конкретного чата), не только «принять всё» или «отклонить всё».
4. **`user_edited` фиксируется на уровне каждого пункта плана**, не только агрегированно — это прямая метрика KPI «AI-предложения приняты без правок ≥80%» (override-rate в audit log).
5. **Snapshot в undo_log — до apply, не после (write-ahead).** Если запись snapshot не удалась — apply для этого пункта плана не должен выполняться. Это защита от «применили, а откатить не можем», прямое требование NFR «Надёжность».
6. **Throttled apply** — см. скилл `rate-limiter`, пайплайн apply не имеет права обходить throttled-обёртку.
7. **Audit log пишется для каждого применённого действия (FR-14)**, включая достаточно данных, чтобы построить undo (ссылка на undo_log) и объяснить пользователю, что произошло.
8. **Undo (FR-15) — на уровне отдельного действия**, не только «откатить всё с начала». Пользователь должен иметь возможность отменить конкретный пункт из audit log.
9. **Soft-delete (FR-16).** Удаление чата — это перемещение в «Архив» на 30 дней, а не необратимая операция того же уровня, что реальное `delete_history`.
10. **Double-flag на опасные действия** (`delete_history`, `leave_*`) — см. `docs/SECURITY.md` §5 и скилл `telethon-safety`. Human-in-the-loop для этих действий состоит из двух явных шагов, не одного экрана с одной кнопкой.

## Границы ответственности backend / frontend

- **Backend (Codex):** гарантирует инварианты пайплайна (write-ahead snapshot, throttling, audit log) на уровне API — независимо от того, что показывает UI. Frontend не может «обойти» dry-run, отправив запрос напрямую в обход контракта.
- **Frontend (Gemini/Antigravity):** строит UI строго по `docs/API_CONTRACT.md` — экран dry-run, editor плана, экран double-confirm для опасных действий. UI не изобретает собственную логику подтверждения поверх/вместо той, что определена в контракте.

## Тестирование

- Интеграционный тест полного цикла: collect (fake client) → classify → plan → dry-run → apply → undo — должен быть частью test harness Этапа 2 (`docs/TASKS.md`, S2-06).
- Тест на сбой посреди apply: процесс падает после snapshot, но до реального вызова Telegram — при рестарте состояние должно быть согласовано (не «уже применено» и не «потеряно»).
- Ручной прогон на песочном аккаунте: минимум 1 полный цикл apply → undo, зафиксированный как pass/fail (KPI MVP, `docs/PRD.md` §1).
