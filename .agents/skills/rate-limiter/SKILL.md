# SKILL: rate-limiter

> Для кого: 🏗️ Codex. Читать перед реализацией любого кода, делающего batch-запросы к Telegram API (collect, apply).

## Зачем этот скилл

Telegram не публикует точный лимит запросов в секунду для MTProto (constraint «Flood Control», `docs/PRD.md` §5). Продукт балансирует между двумя KPI, которые тянут в разные стороны: скорость (первичный аудит 5000 диалогов ≤ 60 минут, NFR «Производительность») и безопасность аккаунта (0 банов за весь период разработки, KPI MVP). Этот скилл — как балансировать, не изобретая заново при каждой задаче.

## Модель: проактивная пауза + реактивная обработка

Два механизма работают вместе, не взаимоисключающе:

1. **Проактивная пауза.** Между запросами к Telegram — управляемая задержка по умолчанию, до того как Telegram успеет пожаловаться. Не «шлём максимально быстро, пока не получим ошибку».
2. **Реактивная обработка `FloodWaitError`.** Когда Telegram всё же вернул `FloodWaitError(seconds=N)`, обёртка обязана: подождать ровно `N` секунд (не меньше — не пытаться «обмануть» таймер), сообщить о паузе наверх (для WS-прогресса/CLI, FR-21), и только потом повторить запрос. Не глотать ошибку молча, не ретраить агрессивнее исходного темпа.

## Жёсткие правила

1. **Каждый вызов к Telegram API проходит через единую throttled-обёртку**, не через прямой `client.something()` в бизнес-логике. Обёртка — единственное место, которое знает про паузы и `FloodWaitError`.
2. **Бюджет разный для read и write.** Мутирующие операции (создание папок, перемещение чатов) должны иметь более консервативный темп, чем чтение метаданных — цена ошибки выше (см. `docs/SECURITY.md`, модель угроз).
3. **Пауза настраивается, не хардкодится россыпью по коду.** Один источник конфигурации темпа (константа/конфиг), не разбросанные `time.sleep(0.5)` в разных функциях.
4. **Прогресс должен быть видимым во время паузы**, не «зависшим» UI без объяснений — WS-сообщение с `type: flood_wait` и `retry_after_seconds` (см. `docs/API_CONTRACT.md` §4), либо эквивалент в CLI (progress bar, FR-21).
5. **Инкрементальность (FR-20).** Collect должен уметь продолжить с курсора (date/id) после сбоя или ручной остановки — не начинать сбор с нуля, это лишняя нагрузка на API и лишний риск.
6. **Никакого параллелизма поверх throttling.** Не пытаться «ускорить» через несколько одновременных запросов — throttled-обёртка последовательна по дизайну (см. `docs/ADR/0003-asyncio-not-celery.md` — не воркеры, а один процесс с последовательным async).

## Метрики, по которым проверяется баланс

| Метрика | Источник | Как проверить |
|---|---|---|
| Первичный аудит 5000 диалогов ≤ 60 мин | NFR «Производительность» | Замер времени на песочном аккаунте |
| 0 банов/ограничений за весь период разработки | KPI MVP | Наблюдение на песочном аккаунте, история FloodWait-событий |
| Rate limiter корректно проходит симуляцию FloodWait | `docs/ARCHITECTURE.md` §5 | Unit-тест с fake client, эмулирующим `FloodWaitError` |

## Тестирование

- Обязательный unit-тест: симуляция `FloodWaitError` с проверкой, что обёртка ждёт заявленное время и не теряет прогресс (курсор не сбрасывается).
- Тест на «нормальный» батч без ошибок — проверка, что проактивная пауза не делает продукт неприемлемо медленным относительно NFR.
- Реальный прогон — только на песочном аккаунте, с фиксацией результата в `docs/HANDOFF.md`, если обнаружено расхождение с ожидаемым темпом Telegram.
