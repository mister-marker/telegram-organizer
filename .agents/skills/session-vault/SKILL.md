# SKILL: session-vault

> Для кого: 🏗️ Codex. Читать перед любым кодом, который создаёт, читает, обновляет или удаляет сессию авторизации Telegram.

## Зачем этот скилл

Session-строка Telethon — это фактически пароль от аккаунта пользователя: с ней можно делать всё, что может делать сам пользователь. FR-03 требует хранения в системной связке ключей macOS Keychain. Это самый чувствительный компонент всего продукта — ошибка здесь обесценивает все остальные меры безопасности.

## Жёсткие правила

1. **Единственное разрешённое хранилище — macOS Keychain.** Не файл на диске (даже зашифрованный самописным способом), не SQLite, не переменная окружения в `.env`, не сериализация в `plan.json`/логи «на всякий случай».
2. **Ни один процесс записи на диск не должен видеть session-строку в открытом виде.** Если для отладки логируется состояние объекта клиента — session-строка должна быть замаскирована/исключена явно, не «просто не логируем весь объект и надеемся».
3. **Логин пишет сессию в Keychain сразу после успеха**, без промежуточного файла — даже временного, даже с последующим удалением (временные файлы могут пережить креш процесса).
4. **Logout (FR-04) обязан удалять запись из Keychain**, а не только сбрасывать in-memory состояние. Проверяется тестом: после logout повторный запуск не должен находить старую сессию.
5. **Оба метода авторизации (FR-01 телефон+код, FR-02 QR) сходятся в одну и ту же точку записи в Keychain.** Не два разных пути хранения для двух способов логина.
6. **Device fingerprint (Этап 2, `docs/TASKS.md` S2-05)** хранится отдельно от самой сессии и не является заменой Keychain-хранения — это дополнительная защита, не альтернатива.

## Рекомендации по реализации (не жёсткие требования, но здравый смысл)

- На Python/macOS для доступа к Keychain обычно используют `keyring` (обёртка над Keychain Services) — итоговый выбор библиотеки фиксирует Codex, это не архитектурное решение уровня ADR, если библиотека действительно пишет в системный Keychain, а не эмулирует его файлом.
- Проверяйте библиотеку на то, что она действительно использует Keychain Services API, а не fallback на файл при отсутствии доступа — такой fallback должен быть либо запрещён, либо явно виден пользователю как деградация.

## Security-CI проверка (обязательна перед PR, `docs/SECURITY.md` §7)

Grep по кодовой базе: отсутствуют пути записи файлов, в имени переменной/параметра которых встречается `session`/`session_string`, кроме обращений к Keychain API. Ложные срабатывания (например, тестовые фикстуры с fake session для unit-тестов на fake client) должны быть явно помечены как тестовые данные, не реальные.

## Тестирование

- Unit-тест: после `login()` сессия физически отсутствует ни в одном файле проекта (grep по временной директории теста).
- Unit-тест: после `logout()` повторный `is_authenticated()` возвращает `False`, и Keychain-запись отсутствует.
- Ручная проверка на песочном аккаунте перед первым релизом Этапа 2: открыть Keychain Access.app, убедиться, что запись действительно там, а не эмулируется файлом рядом.
