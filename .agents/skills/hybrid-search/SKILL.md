# SKILL: hybrid-search

> Для кого: 🏗️ Codex (индексация, поиск), 🎨 Gemini/Antigravity (UI поиска и цитат). Актуально с Этапа 4 «AI Classification» (`docs/ARCHITECTURE.md` §1) — до этого момента полноценный семантический поиск не реализуется, скилл фиксирует правила заранее.

## Зачем этот скилл

Saved Messages и избранные каналы превратились в «кладбище ссылок» (`docs/PRD.md` §1) — поиск по названию бесполезен, если пользователь не помнит, как называлась ссылка. Задача — поиск по смыслу, но без ложной уверенности: продукт обязан честно говорить «не нашёл», а не галлюцинировать релевантный ответ.

## Жёсткие правила

1. **Индексация — только opt-in (FR-24).** Saved Messages и избранные каналы индексируются только после отдельного явного согласия пользователя — это третий уровень consent, отдельный от общего запуска и от opt-in чтения топ-N чатов (FR-06). Не переиспользуйте один и тот же флаг согласия для разных уровней доступа.
2. **Гибридность обязательна (FR-25): FTS + векторы, не только одно из двух.** Full-text search (SQLite FTS5, `docs/ARCHITECTURE.md` §1, Этап 4) ловит точные совпадения и редкие термины; embeddings (bge-m3 через Ollama) ловят смысл при других формулировках. Чистый vector-search без FTS теряет точные цитаты и имена; чистый FTS не понимает перефразирования.
3. **Embeddings — строго локально.** Ollama работает на Mac пользователя, не выходит за его пределы (`docs/ARCHITECTURE.md` §2, C4 Context). Не отправлять текст сообщений во внешний API для векторизации, даже «для качества» — это нарушает local-first (`docs/ADR/0001-local-first.md`).
4. **Генерация ответа (RAG) и тегирование через LLM Providers (BYOK) — opt-in функция.** Вызов LLM для генерации ответа или тегирования должен идти через абстрактный интерфейс `LLMProviderInterface` (ADR-0005). Система читает активный API-ключ пользователя (OpenAI, Anthropic, Custom) из Keychain. Поиск не должен ломаться при отсутствии ключа — если облачный LLM-провайдер не настроен, поиск гибко деградирует в выдачу релевантных сообщений без AI-суммаризации.
5. **Каждый результат поиска — с цитатой (FR-25): чат, дата, msg id.** Ответ LLM (RAG) строится ТОЛЬКО из retrieved-контекста. Ответ без возможности проверить источник в исходном чате не отдаётся пользователю как факт.
6. **Честное «не нашёл».** Если релевантность ниже разумного порога — продукт должен сказать «не нашёл», не выдавать наименее плохой вариант с видом уверенного ответа. Порог — предмет калибровки Codex при реализации, но сам принцип не опционален.
7. **Бюджет ресурсов.** Локальные LLM/embeddings ≤ 3B параметров (constraint «RAM 8GB», `docs/PRD.md` §5) — это ограничивает выбор модели embeddings и любого локального re-ranking, если он появится.
8. **Пользовательские правила из правок (FR-26)** («чат X — всегда категория Y») — не часть поиска напрямую, но используют ту же инфраструктуру индексации/классификации; не дублировать логику отдельно.

## Производительность

- Дашборд/поиск < 2с, p95 < 1.5с (NFR «Производительность») — гибридный запрос (FTS + vector) должен укладываться в этот бюджет, включая агрегацию двух источников результатов. Вызов сторонней LLM для суммаризации (RAG) считается отдельным асинхронным этапом после выдачи быстрых результатов.
- Полное opt-in-индексирование может занимать до 24 часов (NFR, отдельная метрика от «60 мин на 5000 диалогов» — это про метаданные, не про полный текстовый индекс) — должно быть фоновым и прерываемым/возобновляемым, не блокирующим остальной продукт.

## Тестирование

- Unit-тест на «честное не нашёл»: запрос, заведомо не имеющий релевантных совпадений, не должен возвращать результат с высокой уверенностью.
- Тест на цитаты: каждый результат гибридного поиска содержит валидный `(chat, date, msg_id)`, который можно сопоставить с исходным сообщением.
- Тест деградации: при отсутствии настроенных API-ключей (BYOK) поиск и категоризация продолжают успешно работать локально на rules+embeddings.
