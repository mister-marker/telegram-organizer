# SKILL: telethon-safety

> Для кого: 🏗️ Codex (весь код, работающий с Telethon/MTProto). Читать перед написанием любой функции, вызывающей Telegram API.

## Зачем этот скилл

Telegram официально не публикует условия, при которых userbot получает ограничение или бан (constraint «TOS», `docs/PRD.md` §5). Единственная защита — дисциплинированный код: read-only по умолчанию, явное согласие на всё, что не является метаданными, и человекоподобный паттерн запросов. Этот файл — что именно значит «дисциплинированный» в коде.

## Жёсткие правила

1. **Read-only по умолчанию (FR-17).** Любая функция, которая читает Telegram API, не должна иметь побочных эффектов мутации, пока пользователь явно не включил assisted-режим. Если сомневаетесь, читает функция или меняет — трактуйте как «меняет» и требуйте explicit-флаг.
2. **Dry-run перед apply (FR-18).** Каждая мутирующая операция (переместить чат, создать папку, архивировать) должна иметь режим предпросмотра, который не делает реальных вызовов записи в Telegram.
3. **Опасные методы — под double-flag.** `delete_history`, `leave_channel`/`leave_chat` и их аналоги запрещены к вызову без двух независимых подтверждений на уровне выше этого кода (UI/CLI слой) — сам метод-обёртка должен принимать `confirm_1: bool, confirm_2: bool` или эквивалент, а не один флаг `force=True`. См. `docs/SECURITY.md` §5.
4. **Чтение содержимого сообщений — только opt-in (FR-06).** До 50 сообщений на чат, только для топ-N активных чатов в первом прогоне, только после отдельного consent-экрана (не того же самого, что общее согласие на запуск). Метаданные (заголовок, тип, участники, дата, unread) не требуют этого согласия — не путайте два уровня доступа в одной функции.
5. **Session-строка никогда не покидает Keychain-слой.** Обёртки Telethon получают уже готовый `StringSession`/client, не читают и не логируют сырую строку сессии. Детали — скилл `session-vault`.
6. **Ничего не логируется дословно.** Тела сообщений (`message.text`, `message.raw_text`) не передаются ни в один логгер ни на каком уровне (включая `debug`). См. `docs/SECURITY.md` §3.
7. **Каждый мутирующий вызов проходит через throttled-обёртку.** Никаких прямых вызовов `client.something()` для операций, перечисленных в FR-11–13, FR-16 — только через слой rate limiter (скилл `rate-limiter`). Это не опционально даже для «одного маленького вызова в тесте».
8. **Один сеанс — один клиент.** Не открывать параллельные Telethon-клиенты на одну и ту же сессию/номер — это триггерит поведение, похожее на компрометацию аккаунта, и увеличивает риск бана.

## Consent-экран: что именно требует согласия

| Действие | Нужен consent? | Комментарий |
|---|---|---|
| Список диалогов, метаданные | Нет | FR-05, базовая функциональность |
| Чтение до 50 сообщений в топ-N чатах | Да, отдельный экран | FR-06 |
| Индексация Saved Messages / избранных каналов | Да, отдельный опт-ин | FR-24 |
| Облачное тегирование через Token Router | Да, отдельный опт-ин | Не путать с opt-in на чтение — это два разных согласия |
| Любая мутация (папки, архив, удаление) | Да, dry-run + подтверждение | FR-17/18 |

## Тестирование

- Разработка и любые «пробные» вызовы — только на песочном аккаунте (правило CEO, `AGENTS.md` §2). Никогда не тестировать мутирующий код на основном аккаунте.
- Unit-тесты Telethon-обёрток используют fake client (`docs/ARCHITECTURE.md` §1, Этап 2, `backend/tests/`) — не реальный API даже в CI.
- Перед PR: grep-проверка по этому скиллу — есть ли в диффе вызовы `delete_history`/`leave_*` без double-flag (см. `docs/SECURITY.md` §7, пункт 1).

## Если задача противоречит этому скиллу

Остановиться и сообщить CEO через `docs/HANDOFF.md`, а не искать обходной путь (например, «временно» логировать текст для отладки). Это прямое требование мастер-промпта в `AGENTS.md` §4.
