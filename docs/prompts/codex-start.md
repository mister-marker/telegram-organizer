## Твоя первая задача

Открой `docs/TASKS.md`, раздел «Этап 2». Конкретное состояние каждого пункта уже сверено с реальным кодом:

- **S2-01 (rate limiter):** уже сделано в обеих частях — `ratelimit.py` содержит и фиксированную проактивную паузу (`PACE_SECONDS = 1.0`), и реактивную обработку `FloodWaitError`. Не переписывай механизм с нуля. Осталось: провалидировать реальный темп на песочном аккаунте и, если понадобится, сделать паузу адаптивной (сейчас она константа, не подстраивается под нагрузку) — скилл `rate-limiter`.
- **S2-02 (session vault):** сейчас сессия — обычный `.session`-файл (SQLite, через `TelegramClient(settings.session_name, ...)` в `tg_client.py`), не зашифрован. Перенести в macOS Keychain — скилл `session-vault`.
- **S2-03 (undo):** `undo_log.jsonl` уже пишется с состоянием «до» для каждого действия — но **после** успешного вызова Telegram API (см. `actions.py`, `_log_action()` вызывается уже после `await with_flood_control(...)`), не до. Это расходится с write-ahead из `docs/ARCHITECTURE.md` §4 и NFR «Надёжность»: если процесс упадёт в узком окне между успешным вызовом и записью в лог, действие останется без записи для отката. При добавлении команды `undo` заодно поправь порядок — запись в лог должна происходить до реального вызова API, не после. Для папок откат сложнее, чем для archive/mute, читай примечание в README.
- **S2-04 (валидация лимитов):** сейчас лимиты папок (10/100 без Premium, 20/200 с Premium) не проверяются заранее — Telegram сам возвращает ошибку. Нужна предвалидация до apply.
- **S2-05 (device fingerprint):** с нуля, в текущем коде этого нет.
- **S2-06 (test harness):** с нуля — pytest + fake Telethon client, тестов сейчас нет вообще.
- **S2-07 (security-CI):** grep-проверки из `docs/SECURITY.md` §7 как pre-commit/CI шаг.
- **BL-06 (Dockerfile, параллельно):** второй канал дистрибуции для друзей-разработчиков CEO, не альтернатива Tauri (Этап 5) — это его собственное решение, см. `docs/ARCHITECTURE.md`, заметка про Docker. Сессия внутри контейнера — по правилам `docs/SECURITY.md` §2a, не Keychain (в Linux-контейнере его нет).

`actions.py` уже реализует `leave_dialogs` с double-flag (`--yes` + `--confirm-leave`) — это готовый референс-паттерн для будущих опасных действий, не изобретай его заново для других мутаций такого уровня.

## Жёсткие правила (напоминание, полный список — `AGENTS.md` §4)

Read-only по умолчанию. Dry-run перед любой мутацией. Session-строка никогда не в логах/БД/коммитах. Тексты сообщений пользователя никогда не в логах. `delete_history`/`leave_*` — только с двойным флагом. Массовые запросы — только через throttled-обёртку. Разработка и тесты — только на песочном аккаунте, ты никогда не трогаешь основной аккаунт CEO.

Открывай ветку `stage/*` или `fix/*`, атомарные коммиты, осмысленные сообщения (`feat(actions): add proactive rate limiting`). Не мерджишь сам — только CEO через `git merge --no-ff`. Не редактируешь `frontend-worktree/` (появится с Этапа 3) ни при каких обстоятельствах.

Если задача противоречит PRD/ARCHITECTURE/SECURITY — остановись, зафиксируй в `docs/HANDOFF.md` и сообщи CEO, не додумывай решение сам.

## Образовательный фокус (Для CEO)
Поскольку этот проект является не только утилитой, но и базой для перехода к серьезной ИИ-инженерии, твой код должен быть кристально понятным. 
- Обязательно комментируй логику работы всех базовых функций.
- Детально расписывай механику работы асинхронных циклов (`async for`) при итерации по диалогам и массивам данных. 
- Объясняй, как именно обрабатываются потоки данных под капотом (например, как работают `yield` или очереди `asyncio.Queue`).
Код должен стать прочным фундаментом для глубокого понимания бэкенд-фреймворков и паттернов проектирования.
