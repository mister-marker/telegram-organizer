## 1. Эволюция продукта (Этапы 1–7)

Единственная версия таблицы этапов — дублей в исходниках не найдено (лист `таблица этапов`, без скрытых строк/столбцов).

| Этап | Название | Что делаем | Технический стек | Результат |
|---|---|---|---|---|
| 1 | CLI Baseline ✅ | Read-only аудит, rule-based классификация, manual edit plan.json | Telethon, SQLite (файлы), Rich CLI | Пользователь видит статистику и может вручную править план |
| 2 | Undo + Safety | Команда undo, проактивный rate limiting, валидация лимитов папок, device fingerprint | Telethon, SQLite (файлы), Rich CLI + pytest, fake client | Безопасные изменения с откатом, защита от FloodWait |
| 3 | Web Dashboard | Локальный веб-интерфейс: статистика, drag-and-drop редактор плана, WS-прогресс, история действий | FastAPI + React + Vite + Tailwind + WebSocket | Удобный UI для управления планом |
| 4 | AI Classification | Локальные embeddings (bge-m3), opt-in cloud tagging (kimi-k3-free), семантический поиск по Saved Messages | Ollama + LanceDB/pgvector + Token Router | Умная категоризация по смыслу переписки |
| 5 | Desktop App | Упаковка в нативное приложение: Tauri (Rust + React), DMG для macOS, автозапуск, системные уведомления | Tauri + системный keychain | Готовый к дистрибуции desktop-продукт |
| 6 | Multi-device Sync | Supabase/PostgreSQL для синхронизации метаданных и плана между устройствами, инкрементальная синхронизация | Supabase + pgvector + WebSocket | Работа на Mac + Windows + Linux с общей базой |
| 7+ | Cloud + Mobile | Опциональный облачный режим (managed hosting), мобильные приложения (React Native), Telegram Mini App как пульт, монетизация через Stars | Cloud infra + React Native + Stars API | Массовый продукт с подпиской |

Логика последовательности: **сначала безопасность и локальность (1–2), затем удобство (3), затем интеллект (4), затем дистрибуция (5), и только потом — сеть и деньги (6–7).** Ни на одном из этапов 1–5 продукт не требует сервера или доверия облаку — прямое следствие constraint «Юридическое» (только собственные данные пользователя) и модели распространения local-first из PRD (`docs/ADR/0001-local-first.md`).

> ℹ️ **Docker как второй канал дистрибуции (добавлено CEO, 16.08.2026).** Ни `.docx`, ни `.xlsx` не описывают Docker-упаковку явно как часть таблицы этапов — это осознанное дополнение CEO поверх исходников, не из них. Смысл: Tauri (Этап 5) — канал для конечных пользователей; Docker — параллельный, более ранний канал, чтобы делиться CLI-ядром (уже готовым с Этапа 1) с друзьями-разработчиками для обратной связи, не дожидаясь нативной упаковки. Оба local-first — контейнер запускается на машине каждого конкретного пользователя, не на общем сервере, поэтому не противоречит `docs/ADR/0001-local-first.md`. Технический нюанс: Docker-контейнер обычно на Linux — там нет macOS Keychain, поэтому хранение сессии для этого канала требует отдельной схемы (см. `docs/SECURITY.md` §2a). Задача на реализацию — `docs/TASKS.md`, BL-06.

> ⚠️ **Уточнение к строке Этапа 4 (16.08.2026).** В `.xlsx` технический стек указан как «LanceDB/pgvector» через слэш — выглядит как незакрытый выбор. Это ложная развилка: pgvector требует Postgres, а Postgres по `docs/ADR/0002-sqlite-not-pg.md` не появляется в проекте раньше Этапа 6. На Этапе 4 единственный вариант, не ломающий уже принятый ADR-0002 — **LanceDB** (embedded, без отдельного сервера). pgvector становится актуален только вместе с Supabase на Этапе 6 (`docs/ADR/0004-supabase-later.md`), где это часть одного и того же решения, а не альтернатива LanceDB на более раннем этапе.

## 2. C4 Context

```
Пользователь ──(дашборд / CLI)──> TG Organizer (локально на Mac)
                                          │  throttled MTProto
                                          ▼
                                   Telegram MTProto

TG Organizer ──(LLM Provider Interface)──> [Выбор пользователя]
     ├─> Ollama (локально, бесплатно)
     ├─> Anthropic API (по API-ключу пользователя)
     ├─> OpenAI API (по API-ключу пользователя)
     └─> Custom URL (TokenRouter и др., по ключу пользователя)
```

Ключевое решение, видное на диаграмме: Telegram MTProto работает всегда (под throttling), а Ollama не выходит за пределы Mac. Все остальные исходящие соединения (OpenAI, Anthropic, Token Router) инкапсулированы в абстракцию LLM Provider Interface и работают исключительно по принципу BYOK (Bring Your Own Key) с явного согласия пользователя. 

## 3. Data Flow (Logic → Bridge → Presentation)

```
Logic Layer (backend/)
        │  updates specs
        ▼
Bridge Layer (docs/API_CONTRACT.md)   ← единственный источник правды
        │  single source
        ▼
Presentation Layer (frontend-worktree/)
```

Прямое следствие для процесса: Codex и Gemini/Antigravity никогда не редактируют файлы друг друга — единственная точка синхронизации между backend и frontend — `docs/API_CONTRACT.md` (см. `AGENTS.md`, §1 и §2).

## 4. Пайплайн apply (BPMN-подобная схема)

```
collect метаданных
        │
        ▼
классификация: rules + AI
        │
        ▼
plan-манифест  ⇄  правки (пользователь редактирует план)
        │
        ▼
подтверждение пользователя
        │  apply
        ▼
snapshot в undo_log        ← запись ДО изменения (write-ahead, NFR «Надёжность»)
        │
        ▼
throttled apply             ← с обработкой FloodWaitError
        │
        ▼
audit log
        │
        ▼
undo? ──да──> восстановление из undo_log
```

Прямая реализация FR-14 (audit log), FR-15 (undo), FR-17/FR-18 (read-only + dry-run по умолчанию) и NFR «Надёжность» (undo_log пишется до apply, возобновление с курсора после сбоя). Из этой схемы выведен `UC-01` в `docs/PRD.md`, §6.

## 5. Модули безопасности

Краткая версия — полный threat model, security-CI проверки и инцидент-план в `docs/SECURITY.md`.

### Keychain (хранение сессии)

- Сессия пользователя хранится в зашифрованном виде в системной связке ключей **macOS Keychain** (FR-03) — не в файле и не в БД.
- NFR «Безопасность»: только Keychain; тексты сообщений никогда не попадают в логи.
- Security-CI (grep-тесты, PRD §«Требования к тестированию»): в коде отсутствуют `delete_history`/`leave_*` без двойного флага; сессия не пишется в файлы/БД; в логах нет текстов сообщений.

### Rate Limiter

- Telegram официально не публикует точный лимит запросов в секунду для MTProto — заложенный механизм: **проактивная пауза + реактивная обработка `FloodWaitError`** (constraint «Flood Control», FR-07).
- Unit-тест: rate limiter должен корректно проходить симуляцию FloodWait.
- Метрика NFR: первичный аудит 5000 диалогов ≤ 60 минут — то есть rate limiter должен быть достаточно быстрым, но не настолько агрессивным, чтобы триггерить лимиты Telegram; баланс проверяется на песочном аккаунте (KPI «0 банов за весь период разработки»).

### Consent-экран и LLM Провайдеры (BYOK)

- Юридическое ограничение: обработка только собственных данных пользователя; явный consent-экран перед любым чтением текстов (не только метаданных).
- Облачное тегирование через сторонние API (Token Router, OpenAI, Anthropic) — это компоненты, работающие только с согласия пользователя по паттерну BYOK. Пользователь сам вводит ключи, которые хранятся так же безопасно, как и сессия Telegram. Бюджетное ограничение: free-тариф Token Router (kimi-k3-free) доступен только до 31.08, после чего система гибко переключается на других провайдеров или деградирует в локальные rules+embeddings.
