# SECURITY.md — Threat model и правила безопасности

> Собрано из `docs/ARCHITECTURE.md` §5 «Модули безопасности», `docs/PRD.md` (FR-01–04, FR-16–19, FR-23, constraint «TOS», constraint «Юридическое», NFR «Безопасность») и мастер-промпта в `AGENTS.md` §4. Это разворачивающая версия — источник правды по требованиям остаётся в PRD, здесь — как их реализовать и проверить. Каждый агент обязан прочитать этот файл перед задачами, касающимися Telethon, хранения данных или мутирующих действий.

## 1. Модель угроз

| Актор/сценарий | Риск | Митигация |
|---|---|---|
| Утечка session-строки | Полный доступ к аккаунту пользователя третьей стороной | Хранение только в macOS Keychain (FR-03), запрет записи в файлы/БД/логи/git — см. §2 и скилл `session-vault` |
| Бан/ограничение аккаунта Telegram (TOS) | Потеря доступа к аккаунту, к которому применяется инструмент | Разработка и тесты — только на песочном аккаунте (правило CEO в `AGENTS.md`); throttled apply, проактивный rate limiting — см. скилл `rate-limiter` |
| Скрытое чтение переписки без согласия | Нарушение приватности, юридический риск («Обработка только собственных данных пользователя», constraint «Юридическое») | Read-only по умолчанию (FR-17), consent-экран перед любым чтением текстов, чтение содержимого — только opt-in и только для топ-N чатов (FR-06) |
| Необратимое разрушительное действие (delete_history, leave_*, мгновенный apply) | Потеря данных пользователя, невозможность отката | Double-flag confirmation, dry-run по умолчанию (FR-18), snapshot в undo_log до apply (write-ahead), soft-delete на 30 дней (FR-16) |
| Незаметная отправка данных в облако | Скрытая утечка переписки в сторонний сервис (Token Router) | Token Router — единственный компонент с исходящим каналом, требующим согласия; экран сетевой прозрачности (FR-23) должен показывать каждое исходящее соединение |
| Агент (Codex/Aider/Gemini) галлюцинирует и пишет опасный код | Обход всех вышеперечисленных митигаций из-за ошибки агента, а не злого умысла | Security-CI grep-проверки перед мерджем (см. §5), Aider-аудит перед PR, CEO — единственный, кто мерджит в `main` |

## 2. Хранение сессии

- Единственное разрешённое место — системная связка ключей **macOS Keychain** (FR-03). Не файл, не SQLite, не переменная окружения в `.env`, не in-memory кэш, переживающий рестарт в незашифрованном виде на диске.
- Логика логина (FR-01 телефон+код, FR-02 QR) должна писать сессию в Keychain сразу после успешной авторизации, не создавая промежуточных файлов на диске даже временно.
- Logout (FR-04) обязан удалять запись из Keychain, а не просто «забывать» её в памяти процесса.
- Подробные правила реализации — скилл `.agents/skills/session-vault/SKILL.md`.
- Хранение сторонних API-ключей (OpenAI, Anthropic и др.): Подчиняются тем же строгим правилам, что и Telegram-сессия. Все API-ключи (BYOK) должны сохраняться исключительно в macOS Keychain (или через аналогичный безопасный менеджер паролей операционной системы). Хранение ключей в открытом виде в database.sqlite строго запрещено. 
- Запрет экспозиции: API-эндпоинты (например, /api/v1/settings/llm) НИКОГДА не должны возвращать сами API-ключи на фронтенд. Фронтенд должен получать только статус {"is_configured": true} или маскированную версию {"key_preview": "sk-...****"}.

### 2a. Исключение: хранение сессии в Docker-канале (не macOS)

Правило «только Keychain» (FR-03) писалось для нативного macOS-канала (Tauri, Этап 5). Docker-контейнер (`docs/ARCHITECTURE.md` §1, заметка о втором канале дистрибуции) обычно запускается на Linux — там macOS Keychain физически недоступен, это не обходной путь, а другая операционная среда.

Для этого канала: session-строка хранится **зашифрованной** в файле внутри volume контейнера — не в открытом виде и не в образе (`.session`/session-строка не должна попадать в `docker build`, только монтироваться как runtime volume). Шифрование — уже осознанно заложено в README текущего скелета (`cryptography.fernet`) как план для Этапа 3, тот же механизм переиспользуется здесь. Ключ шифрования — не в коде и не в образе: переменная окружения, которую задаёт сам пользователь контейнера при первом запуске, не значение по умолчанию.

Что не меняется независимо от канала: read-only по умолчанию (FR-17), запрет на тексты сообщений в логах, double-flag на опасные действия. Docker как более лёгкий канал распространения не даёт права ослаблять эти правила «для простоты».

## 3. Что никогда не попадает в логи

- Тексты сообщений пользователя (NFR «Безопасность») — ни в structured logs, ни в traceback при исключениях, ни в debug-принтах.
- Session-строка / токен авторизации.
- Полное содержимое ответов Telegram API, если в них есть текст сообщений — логировать можно метаданные (id чата, тип события, длительность запроса), не тело.
- Данные, отправленные в Token Router (opt-in) — не логируются локально сверх того, что нужно для audit log (какой чат был протегирован, не содержимое).

## 4. Consent и сетевая прозрачность

- Явный consent-экран обязателен перед первым чтением содержимого сообщений (FR-06) — отдельно от базового разрешения на запуск приложения. Man-in-the-middle попытки «согласился один раз на всё» недопустимы: opt-in чтения текстов — отдельное действие пользователя от opt-in Token Router.
- Экран сетевой прозрачности (FR-23) — список исходящих соединений в реальном времени: Telegram MTProto (всегда) и Token Router (только если включён). Ollama не показывается в этом списке, так как не выходит за пределы Mac (docs/ARCHITECTURE.md §2, C4 Context).
- Экран сетевой прозрачности (FR-23) должен показывать все исходящие соединения. Поскольку на Этапе 4 вводится BYOK-интерфейс, пользователь должен четко видеть, какому именно LLM-провайдеру (OpenAI, Anthropic, Token Router) сейчас уходят данные для тегирования.

## 5. Опасные действия и double-flag confirmation

Действия, требующие двойного подтверждения (не проходят с одним `--yes`):

- `delete_history` / любой аналог полного удаления истории чата.
- `leave_*` (выход из группы/канала), если это необратимо влияет на членство пользователя.
- Любой batch-apply, помеченный как затрагивающий > N чатов одновременно (порог фиксирует Codex в реализации, не ниже здравого смысла — не должен позволять снести всю структуру одной командой без явного второго подтверждения).

Правило soft-delete (FR-16): чат при удалении сначала уходит в «Архив» на 30 дней, а не удаляется физически сразу — это первый уровень защиты ещё до undo_log.

## 6. Rate limiting и Flood Control

Полные правила — скилл `.agents/skills/rate-limiter/SKILL.md`. Кратко: проактивная пауза между запросами + реактивная обработка `FloodWaitError`, баланс между скоростью (NFR: 5000 диалогов ≤ 60 мин) и риском бана (KPI: 0 банов за весь период разработки на песочном аккаунте).

## 7. Security-CI проверки (grep-тесты перед мерджем)

Обязательный минимум, который должен проходить перед PR → CEO Merge Approval (расширяется по мере роста кодовой базы):

1. В коде отсутствуют вызовы `delete_history`/`leave_*` без двойного флага подтверждения.
2. Session-строка/токен не записывается ни в один файл вне API Keychain (grep по путям записи файлов рядом с любым упоминанием `session`).
3. В коде логирования (`logger.*`, `print`, structured logging) нет прямой передачи тела сообщения Telegram (`message.text`, `message.raw_text` и аналогов) в лог.
4. `.env`/конфиги в репозитории не содержат реальных токенов/номеров телефона/session-строк (secrets-сканер или простой grep по паттернам).
5. Каждый apply-путь проверяется на наличие записи в `undo_log` **до** фактического изменения (write-ahead), не после.

Aider (QA/Аудитор) прогоняет этот список как часть аудита перед каждым PR — см. `AGENTS.md` §2, роль Aider.

## 8. Что делать при инциденте

- **Подозрение на бан/ограничение песочного аккаунта:** остановить все apply-операции, зафиксировать в `docs/HANDOFF.md`, разобрать причину (слишком агрессивный rate limiter?) прежде чем продолжать разработку на этом или любом другом аккаунте.
- **Утечка session-строки (обнаружена в логах/коммите):** немедленно инвалидировать сессию через Telegram (завершить сессию удалённо), исключить файл из истории git, найти и закрыть источник утечки, обновить security-CI проверку, чтобы конкретно этот случай ловился автоматически.
- **Основной (не песочный) аккаунт случайно затронут:** это прямое нарушение правила CEO («единственный, кто трогает основной аккаунт») — расследуется вне зависимости от того, кто/что вызвало действие (агент, баг, человек).

## Вне зоны действия этого документа

Юридическая оценка соответствия TOS Telegram и локальному законодательству — не техническая задача и не решается кодом; здесь фиксируются только технические митигации риска. Формальная оценка правовых рисков — на усмотрение CEO, при необходимости с консультацией юриста.
