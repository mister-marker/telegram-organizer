# Product Requirements Document — Telegram Workspace Organizer

> Источники: `telegram-organizer.docx`, `Эволюция_продукта_telegram-organizer-таблица_этапов_.xlsx`. Заметки о том, что было отфильтровано (и что не найдено) — в конце файла. Диаграммы из `.docx` перенесены в `docs/ARCHITECTURE.md`, роли и git-стратегия — в `AGENTS.md`.

## 1. Цель проекта

**Бизнес-цель.** Создать инструмент, который поможет пользователям Telegram с многолетней историей общения навести порядок в своём цифровом пространстве, превратив хаос из тысяч чатов в структурированную, управляемую систему — не требуя доверия облаку.

**Главная проблема.** Информационная перегрузка и цифровой хаос, накопленные за годы использования Telegram:

- Тысячи чатов, каналов, групп и ботов накапливаются за годы использования.
- Важные диалоги теряются среди спама и неактивных чатов.
- Ручная сортировка такого объёма в интерфейсе Telegram невозможна.
- Нет инструментов для автоматической категоризации и структурирования чатов.
- Saved Messages превратились в «кладбище ссылок» — поиск по ним бесполезен.
- Ручная раскладка 3000+ чатов по папкам = сотни часов; пользователь не начинает вообще.

**KPI на MVP (измеримые):**

| KPI | Тип | Значение |
|---|---|---|
| Время поиска нужного чата | продуктовый | −70% (опрос после 2 недель использования) |
| AI-предложения приняты без правок | продуктовый | ≥80% (override-rate в audit log) |
| Первичный аудит 3000 диалогов | технический MVP | pass/fail на песочном аккаунте, без ручной борьбы с FloodWait |
| Полный цикл apply → undo | технический MVP | ≥1 протестирован на песочном аккаунте, pass/fail |
| Баны/ограничения песочного аккаунта | технический MVP | 0 за весь период разработки, pass/fail |

**KPI на product (перспектива):**

- Пользователь может сократить время на поиск нужного чата на 70%.
- Не менее 80% пользователей успешно применяют предложенную AI-структуру.

## 2. Область применения

| Критерий | Описание |
|---|---|
| Платформы | macOS first (M1/8GB); Windows/Linux — после упаковки |
| Тип продукта | Два независимых канала дистрибуции, не альтернатива друг другу: (1) Tauri (Rust + React) — основной канал для конечных пользователей, DMG для macOS, `docs/ARCHITECTURE.md` §1, Этап 5; (2) Docker-контейнер — параллельный канал для раннего фидбека от друзей-разработчиков, доступен уже на CLI-ядре (Этапы 1–2), не дожидаясь Tauri-упаковки. Оба варианта остаются local-first — каждый пользователь/друг запускает свой контейнер на своей машине, без общего сервера (не противоречит `docs/ADR/0001-local-first.md`) |
| Целевая аудитория | Активные пользователи Telegram с 5+ годами использования, >500 чатов. Ранние адепты: технари с 500+ чатов (способны запустить CLI); далее — массовый пользователь через DMG |
| Модель распространения | Local-first (самостоятельный запуск пользователем), open-source ядро; облачного режима в MVP нет — см. `docs/ADR/0001-local-first.md` |

## 3. Функциональные требования (FR)

### Модуль A: Авторизация и безопасность

| ID | Требование |
|---|---|
| FR-01 | Система должна поддерживать авторизацию через номер телефона и код подтверждения Telegram |
| FR-02 | Система должна поддерживать авторизацию через QR-код (Telegram Desktop-style) |
| FR-03 | Сессия пользователя должна храниться в зашифрованном виде в системной связке ключей macOS |
| FR-04 | Пользователь должен иметь возможность завершить сессию (выйти из аккаунта) |

### Модуль B: Сбор и анализ данных

| ID | Требование |
|---|---|
| FR-05 | Система должна собирать метаданные всех диалогов пользователя: название, тип, количество участников, дата последнего сообщения, количество непрочитанных |
| FR-06 | Чтение до 50 сообщений — только после явного опт-ина и только для топ-N активных чатов в первом прогоне (иначе это скрытое чтение всей переписки без согласия) |
| FR-07 | Сбор данных должен выполняться с учётом ограничений API (паузы при FloodWait) |

### Модуль C: Классификация

| ID | Требование |
|---|---|
| FR-08 | Система должна автоматически классифицировать чаты по категориям: «Работа», «Личное», «Проекты», «Каналы (читать)», «Боты», «Архив», «Спам» |
| FR-09 | Пользователь должен иметь возможность настраивать правила классификации (ключевые слова, исключения) |
| FR-10 | Пользователь должен иметь возможность вручную переносить чаты между категориями (drag-and-drop) |

### Модуль D: Структурирование

| ID | Требование |
|---|---|
| FR-11 | Система должна создавать папки в Telegram для каждой категории чатов |
| FR-12 | Система должна назначать цветные теги папкам; доступность иконок/цветов зависит от Premium и проверяется в рантайме |
| FR-13 | Система должна архивировать неактивные чаты (по выбору пользователя) |

### Модуль E: Управление и откат

| ID | Требование |
|---|---|
| FR-14 | Все действия должны логироваться в истории изменений (audit log) |
| FR-15 | Пользователь должен иметь возможность откатить любое действие (undo) |
| FR-16 | При удалении чат должен сначала перемещаться в «Архив» (мягкое удаление) на 30 дней |

### Модуль F: ключевые решения сверх базового каркаса

| ID | Требование |
|---|---|
| FR-17 | Read-only режим по умолчанию; мутации недоступны до явного включения assisted-режима |
| FR-18 | Dry-run: предпросмотр любого батча изменений до применения |
| FR-19 | Предвалидация плана против лимитов Telegram (папки/чаты, Premium-флаг) до apply |
| FR-20 | Инкрементальная синхронизация метаданных (курсор date/id), возобновление после сбоя |
| FR-21 | Прогресс в реальном времени: WS в дашборде / прогресс-бар в CLI |
| FR-22 | Виртуальные категории внутри приложения (app-side теги) для чатов, не поместившихся в лимиты папок Telegram |
| FR-23 | Сетевая прозрачность: экран со списком исходящих соединений (Telegram + опт-ин LLM Провайдеры) |
| FR-24 | Opt-in индексация Saved Messages и избранных каналов |
| FR-25 | Гибридный поиск (FTS + векторы) с цитатами (чат, дата, msg id) и честным «не нашёл» |
| FR-26 | Пользовательские правила из правок: «чат X — всегда категория Y» |

## 4. Нефункциональные требования (NFR)

| Категория | Требование | Метрика |
|---|---|---|
| Производительность | Первичный аудит метаданных 5000 диалогов | ≤ 60 мин (24 ч — только для полного opt-in-индексирования) |
| Производительность | Дашборд / поиск | < 2 с; p95 < 1.5 с |
| Надёжность | 99.5% uptime → возобновляемость | undo_log пишется до apply (write-ahead); после сбоя — продолжение с курсора, без потери данных |
| Безопасность | Сессия | Только Keychain; тексты сообщений никогда не попадают в логи — детали в `docs/SECURITY.md` |
| Ресурсы | Бюджет на Mac M1/8GB | Приложение ≤ 2 ГБ RAM; локально только embeddings (bge-m3), LLM ≤ 3B и только opt-in |
| Используемость | Запуск анализа | ≤ 3 кликов в дашборде; 1 команда в CLI |
| Масштабируемость | 1000 пользователей → local-first не имеет серверного лимита пользователей | Цель: 5000+ диалогов на пользователя; Этап 6 (Supabase): синхронизация до 1000 устройств |

## 5. Ограничения (Constraints)

| Ограничение | Описание |
|---|---|
| API Telegram | Bot API не позволяет управлять папками → только MTProto (Telethon) |
| Лимиты папок | Без Premium: 10 папок, до 100 чатов в каждой. С Premium: 20 папок, до 200 чатов |
| Flood Control | Telegram ограничивает частоту запросов. Необходимы паузы между запросами |
| TOS | Использование userbot'а может нарушать TOS Telegram → риск бана |
| Оборудование | Минимальные требования: macOS, 8GB RAM, 4GB свободного места |
| RAM 8GB | Запрет на локальные LLM > 3B в MVP |
| LLM Провайдеры (BYOK)| Пользователь использует собственные API-ключи (OpenAI, Anthropic и др.). Локальная Ollama доступна как бесплатная альтернатива. (ADR-0005)|
| Юридическое | Обработка только собственных данных пользователя; явный consent-экран перед любым чтением текстов |

**Use Case UC-01 — «Первичный аудит и структурирование».**

- **Актор:** пользователь.
- **Предусловие:** авторизация в Telegram выполнена (FR-01/FR-02), сессия сохранена в Keychain (FR-03).
- **Основной сценарий:** collect метаданных → классификация rules + AI → plan-манифест → пользователь правит план вручную (FR-09/FR-10) → подтверждение → snapshot в undo_log → throttled apply → audit log.
- **Постусловие:** диалоги разложены по папкам/архиву согласно подтверждённому плану; каждое действие обратимо через undo (FR-15).
- **Альтернативный сценарий:** пользователь отклоняет план на шаге подтверждения → возврат к правкам (цикл «план ⇄ правки»).

*(Полная диаграмма пайплайна, из которой выведен UC-01, — в `docs/ARCHITECTURE.md`, §4 «Пайплайн apply».)*

## 8. Конкуренты и ценность

Существующие Telegram-боты решают задачу управления **будущим**: планирование задач, напоминания, посты — организуют дела. Этот продукт решает задачу управления **прошлым и настоящим**: разобрать хаос из уже существующих тысяч чатов, каналов, групп и сообщений. Это принципиально разные задачи.

| Аспект | Боты-органайзеры (конкуренты) | Этот продукт |
|---|---|---|
| Что делают | Создают новые задачи, напоминания, посты | Анализируют, сортируют, очищают существующий хаос |
| Объект работы | Новые записи пользователя | Вся история чатов пользователя (годы) |
| Проблема | «Как ничего не забыть?» | «Как разобраться в том, что уже накопилось?» |
| Инструмент | Обычный бот (Bot API) | Userbot + глубокий анализ (AI) |
| Сложность | Низкая | Высокая (API, сессии, AI) |
| Приватность | Переписка уходит на сервер бота | Local-first: данные не покидают Mac пользователя |

**Ценность продукта.** Пользователь копит чаты в Telegram годами. Продукт помогает разобрать этот завал за час, не читая переписку и не отправляя данные в облако. Дальше — любой нужный диалог за секунды. Это «менеджер пространства», работающий с прошлым — с тем, что пользователь уже накопил.

**Конкретная ценность для пользователя:**

1. **Экономия времени (измеримая).** Сейчас: поиск нужного чата среди 3000 → 5–10 минут. После: нужный чат в нужной папке → 5–10 секунд. Экономия: 70% времени.
2. **Психологический комфорт.** Сейчас: чувство хаоса, «там всё перемешалось». После: «я знаю, где что лежит». Это как разобрать заваленный годами стол — вы не просто находите вещи, вы перестаёте нервничать от беспорядка.
3. **База знаний (Deep Research).** Сейчас: сохранённые сообщения — «кладбище ссылок». После: поиск по смыслу, цитаты, связанные темы. Это уже не просто органайзер, а личный AI-архив.
4. **Безопасность и приватность (уникально).** Конкуренты (боты) → переписка уходит на их сервер. Здесь → всё локально, на Mac пользователя. Пользователь не доверяет данные никому.

Аналогия: Ежедневник (куда записывают новые задачи) — это конкуренты. Архивариус (который разбирает горы старых бумаг и наводит порядок) — это данный продукт.

## Приложение 3: правка от 16.08.2026 после повторного построчного чтения оригиналов

При прямой сверке с `.docx` и `.xlsx` (не через промежуточные файлы) нашла ещё одну нестыковку: §2 «Область применения» в оригинале называет тип продукта «Desktop-утилита (Electron/Tauri + Python) + локальный Docker-контейнер». Electron в исходниках больше нигде не встречается (стек Этапа 5 явно Tauri) — эту часть убрала. Docker вернула обратно после правки CEO: изначально я прочитала Docker как альтернативу Tauri и как конфликт с ADR-0003 («отказ от лишней инфраструктуры»)  — это была ошибка чтения с моей стороны. ADR-0003 говорит только про Celery/Redis как *очередь задач для фоновой обработки*, а не про упаковку/дистрибуцию приложения — Docker-контейнер как канал распространения не имеет отношения к этому решению. CEO пояснил реальную цель: Docker — это не альтернатива Tauri, а более ранний и лёгкий канал, чтобы поделиться MVP с друзьями-разработчиками для обратной связи, пока Tauri-упаковка (Этап 5) ещё не готова. Формулировка в §2 выше отражает оба канала как независимые.
