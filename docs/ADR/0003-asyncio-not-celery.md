# ADR-0003 — Отказ от Celery на этапах 1–5

**Статус:** принято.

**Контекст.** Более ранние варианты архитектуры этого продукта (обсуждались в предыдущих раундах планирования, до итоговых `.docx`/`.xlsx`) предполагали очередь задач Celery + Redis для фоновой обработки батчей. Ни в `.docx`, ни в `.xlsx` этой связки в итоговой версии уже нет — во всех 7 этапах фигурируют только Telethon/SQLite/Rich CLI (1–2), FastAPI/React/WebSocket (3), Ollama/LanceDB (4), Tauri (5), Supabase (6).

**Решение.** Не использовать Celery/Redis на этапах 1–5. Фоновая работа (throttled apply, инкрементальный collect) реализуется как обычные async-задачи внутри одного локального процесса; прогресс — через WebSocket в дашборде (Этап 3) или прогресс-бар в CLI (FR-21).

**Обоснование.** Celery — инструмент для распределения задач между несколькими воркерами/машинами. При нагрузке «один пользователь, один Mac, один процесс» и жёстком бюджете RAM (≤ 2 ГБ) он добавляет Redis как обязательную зависимость и операционную сложность (мониторинг воркеров, риск зависших задач) без реальной выгоды: throttling и так последовательно ограничивает скорость запросов к Telegram, поэтому распараллеливание через отдельных воркеров не даёт прироста, а только усложняет отладку FloodWait-логики.

**Последствия.** Если на Этапе 6–7 (multi-device / managed hosting) появится реальная многопользовательская серверная нагрузка, это решение стоит пересмотреть отдельным ADR — на данный момент такого требования в PRD нет.

**Связано с:** constraint «Оборудование» (8GB RAM), NFR «Ресурсы», `docs/ARCHITECTURE.md` §1 (таблица «Эволюция продукта», этапы 1–5 не содержат очередей задач).
