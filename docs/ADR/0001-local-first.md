# ADR-0001 — Local-first, без сервера в MVP

**Статус:** принято.

**Контекст.** Продукт работает с многолетней личной перепиской пользователя в Telegram. Constraint «Юридическое» (`docs/PRD.md`, §5) прямо ограничивает обработку только собственными данными пользователя, с явным consent-экраном перед любым чтением текстов. Целевая аудитория MVP (`docs/PRD.md`, §2) — технически подкованные пользователи с 500+ чатами, готовые запустить CLI на собственной машине.

**Решение.** Продукт распространяется как local-first desktop-утилита с open-source ядром. Пользователь запускает её самостоятельно на своей машине (macOS M1/8GB на старте). В MVP (этапы 1–5 из таблицы «Эволюция продукта», `docs/ARCHITECTURE.md` §1) не существует серверного/облачного режима — ни для хранения данных, ни для выполнения логики.

**Обоснование.** Единственный компонент, у которого в принципе может быть доверие к третьей стороне — это опциональный Token Router для облачного тегирования (opt-in, `docs/ARCHITECTURE.md` §2, C4 Context) — и то только с явного согласия пользователя на каждый такой запрос. Local-first architecture — это не просто техническое решение, а прямое условие для доверия пользователя, который по определению не хочет отдавать личную переписку внешнему серверу (см. `docs/PRD.md` §8, «Конкуренты и ценность» — приватность указана как уникальное отличие от ботов-конкурентов).

**Последствия.** Сетевой/облачный режим (managed hosting) откладывается до Этапа 7+ («Cloud + Mobile», `docs/ARCHITECTURE.md` §1) и должен разрабатываться как явно опциональный слой поверх local-first ядра, а не как замена ему. Multi-device синхронизация (Этап 6) вводит первый обязательный сетевой компонент (Supabase) — см. `docs/ADR/0004-supabase-later.md` — но остаётся синхронизацией метаданных/плана, не переносом самой логики на сервер.

**Связано с:** `docs/PRD.md` §2 «Модель распространения», §5 constraint «Юридическое», §8; `docs/ARCHITECTURE.md` §1 (таблица этапов), §2 (C4 Context).
